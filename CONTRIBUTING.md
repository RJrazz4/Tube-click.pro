# Contributing to TubeClick Pro

Thanks for your interest in TubeClick Pro. This document describes how we work: branching, commits, code review, and quality standards.

The repository is private; reach out to the maintainers for access.

---

## Branching Model

- `main` is always deployable. Protection rules require passing CI and one review before merge.
- Feature work happens in short-lived branches named with a conventional-commit prefix:
  - `feat/<short-slug>` — new user-visible capability
  - `fix/<short-slug>` — bug fix
  - `chore/<short-slug>` — tooling, deps, infra
  - `docs/<short-slug>` — documentation-only
  - `refactor/<short-slug>` — behavior-preserving code movement
  - `test/<short-slug>` — tests only

Rebase your branch onto the latest `main` before opening a PR. Avoid merge commits on feature branches.

## Commit Messages

We follow [Conventional Commits](https://www.conventionalcommits.org/) v1.

```
<type>(<scope>): <subject>

<body — optional, wrap at 72 cols>

<footer — optional: BREAKING CHANGE:, Refs #123>
```

- **Types:** `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `chore`, `build`, `ci`, `revert`
- **Scope** is the package or surface: `api`, `orchestrator`, `ui`, `auth`, `referrals`, `seo`, `storyboard`, `thumbnails`, `tts`, `chat`, `clone-crush`, `supabase`, `deps`, etc.
- **Subject** is imperative mood, lowercase, no trailing period, ≤72 characters.
- **Body** explains *why* (not *what* — the diff shows what). Reference tradeoffs you considered.

Examples:

```
feat(referrals): issue HMAC-signed cookie on referral click
fix(api): correct abort-signal leak in _ai.ts retry loop
docs(readme): add architecture diagram and deployment section
chore(deps): bump vite to 5.4.19
refactor(orchestrator): extract tier policy into tiers-handler.ts
test(keys): add conformance tests for poison-key cooldown
```

Do not use AI-attribution footers (`Co-authored-by: <bot>`, "generated by", etc.) in commits. If you use AI assistance, that is fine; the final commit is authored by the human who reviewed it.

## Pull Requests

1. Open a PR against `main`. Fill in the PR template: summary, motivation, testing performed, risk/surface area, screenshots for UI changes.
2. Keep PRs small and focused. A PR that touches both frontend data fetching and Postgres RPCs should usually be two PRs.
3. Ensure CI passes: `npm run ci` (lint + typecheck + tests + verify).
4. Add or update tests for every behavioral change. Bug fixes require a regression test.
5. Update `docs/` when contracts, environment variables, or architecture change.
6. Request one review from a maintainer. Address comments; force-push or add fixup commits and squash before merge (maintainer merges with a single conventional-commit message).

## Code Quality

- **TypeScript `strict: true`** is on for all packages and apps. No implicit `any`.
- **ESLint** warnings are treated as errors in CI; legitimate suppressions are recorded in `eslint-suppressions.json` with a reason in the PR.
- **Tests** live next to the module (`foo.ts` ↔ `foo.test.ts`) for Vitest; e2e tests live in `e2e/specs/`.
- **Comments** explain intent, tradeoffs, and invariants. Do not leave commented-out code, "TODO" without a tracking issue, or narrative journals of development history.
- **No secrets in code or commit messages.** The build verifier (`scripts/verify.mjs`) scans the compiled bundle for API-key patterns; CI will fail if it finds anything.

## Repository Hygiene

- Do not commit generated files (`dist/`, `node_modules/`, `.env`), local editor state (`.vscode/*` except `extensions.json`), or OS metadata (`.DS_Store`). The root `.gitignore` covers these.
- After a feature branch is merged, delete it from the remote.
- Keep `package.json` and `package-lock.json` in sync — never hand-edit the lockfile.

## Release & Deployment

- Every merge to `main` is deployed automatically to production via Vercel's Git integration. There is no separate release branch.
- Migrations are applied to Supabase before the deploying commit lands on `main` (apply in CI against staging, then production, then merge).
- Breaking API changes require a new versioned path (`/api/v2/...`) and a deprecation note on the old path.

## Issues & Security

- Open bug reports and feature requests as GitHub issues with a clear reproduction / user story.
- **Do not open public issues for security vulnerabilities.** Email `support@tubeclickpro.in` with a precise description and reproduction; we respond within 48 hours.
